# Project build settings: projects that build through their own scripts

Some projects don't build with a plain `xtool dev`. A script writes `xtool.yml` (and maybe
`Info.plist`) first, the build needs an environment variable, or the SDK module build needs a higher
open-file limit (`ulimit -n`). Normally the project's own `run.sh` does all of that. Build settings let
iOS Studio build such a project the same way, with its steps, progress, problems and log, without
running the wrapper script.

## The settings

Each project has four, all optional:

| Setting | What it does |
|---|---|
| Prebuild command | Runs in the project folder before every build, re-signing included, as the build's first step ("Running the prebuild command"). Its output goes to the build log. If it fails, the build stops there with one `config` problem that shows the command's last output lines. |
| Environment variables | Added to the environment of the prebuild command and xtool. They replace values you already have, `PATH` included. |
| Open-file limit | The soft `RLIMIT_NOFILE` raised for the build only (the app and your shell keep theirs). Without a setting, every build gets 65536, or the hard limit if that's lower. A value above the hard limit fails before the build starts, with a message saying how to raise the hard limit. |
| Build generated project | Lets iOS Studio build a project whose `xtool.yml` starts with a `GENERATED` comment. Without it such a project is refused, because a stale generated file could build something other than the real app. Pair it with the prebuild command that regenerates the file. |

The prebuild command is split into arguments the way a shell would split it (quotes work), but it
runs **without a shell**: `|`, `&&`, `;`, redirections and `$VARIABLES` don't work, and the first three
are refused when you save. Put steps like that in a script and run the script. A relative program
path (`./generate.sh`) is relative to the project folder; the script needs its executable bit. The
command gets no input, so a script that asks a question reads end-of-file instead of hanging.

## Suggestions

iOS Studio reads the project's `run.sh`, `build.sh`, `generate.sh`, `prebuild.sh` and `xtool.sh` (it
never runs them) and suggests settings from what it finds:

- `export NAME=value` with a literal value becomes an environment variable (not `PATH`, `HOME` and
  other variables of your session, and not values built from `$(...)` or other variables),
- `ulimit -n N` or `ulimit -Sn "$VAR"` with `VAR=N` becomes the open-file limit,
- a `generate.sh` that `run.sh` calls, or the script an `xtool.yml` names in its `GENERATED by …`
  comment, becomes the prebuild command,
- a generated `xtool.yml` turns on Build generated project.

Suggestions are never applied by themselves. They show in the Build settings sheet ("Use these"
fills the form) and in `ios_project_info` / `ios_project_build_settings` (`apply_suggested=true`).
Check the arguments: a script like `generate.sh <API_BASE_URL>` may need one that the suggestion
can't know.

## Where to set them

- **App**: Projects › a project's More › Build settings. The Run, Check build, Build .ipa and
  Re-sign buttons of a generated project stay off, with a tooltip pointing here, until Build
  generated project is on. The error of a refused build has a Build settings button too.
- **MCP**: `ios_project_build_settings(project_path, prebuild=, env=, open_files=, allow_generated=,
  apply_suggested=, confirm=)`. Without changes it shows the settings and suggestions. A change is a
  dry run listing each change until `confirm=true`. `env` merges (a `null` value removes a name).
  `ios_project_info` shows `build_settings` and `suggested_build_settings`. See [mcp.md](../mcp.md).
- **Helper**: `iosstudio-helper projects build-settings --path P [--set '<json>'] [--dry-run]
  [--suggested]`. The JSON patch takes `prebuild`, `env` (merged; `envReplace: true` replaces the
  map), `openFiles` and `allowGenerated`.

They're stored per project in `~/.local/state/ios-studio/projects.json` under
`meta[<path>].build`. Removing a project from the list forgets them.

## Example

A project whose `run.sh` regenerates `xtool.yml` with `generate.sh <url>`, exports
`GARDERI_IOS_CROSS=1` and raises `ulimit -Sn` to 65536:

```
prebuild        ./generate.sh http://192.168.1.20:3000
env             GARDERI_IOS_CROSS=1
open files      65536
build generated on
```

A Run then shows Running the prebuild command, Resolving packages, Compiling, Linking, Signing,
Installing and Launching, like any other project.
